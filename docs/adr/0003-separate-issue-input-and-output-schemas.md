# ADR-0003：分离 Issue 的创建、更新与读取 Schema

- 状态：Accepted
- 日期：2026-09-04

## 背景与约束

Issue 在创建输入、部分更新和读取输出三个方向上的字段所有权不同。调用方可以提供标题、描述和优先级，但 ID、状态和时间由系统管理；部分更新还需要区分“字段未提供”和“主动清空描述”。

如果所有方向共用一个“字段几乎都可选”的模型，调用方可能注入系统字段，缺失的持久化数据也可能被默认值掩盖，后续 Service 和 API 将不得不重复判断数据来自哪里。

## 考虑过的方案

1. 所有数据流共用一个 `Issue` 模型，把大部分字段设为可选。
2. 为创建、更新和读取分别定义 `IssueCreate`、`IssueUpdate`、`IssueRead`。
3. 使用普通字典或 dataclass，在 Service 中手工校验每种输入。

## 决定

选择方案 2，并采用以下边界：

- `IssueCreate` 只接受调用方可控制的内容字段。
- `IssueUpdate` 只接受可普通修改的字段；状态变化由 Service 的专用操作负责。
- `IssueRead` 要求完整的系统字段，不用默认值掩盖数据缺失。
- 所有 Schema 使用 `extra="forbid"` 拒绝未声明字段。
- 校验后的 Schema 使用 `frozen=True` 阻止属性赋值绕过约束。
- 更新中省略字段表示“不修改”，显式 `null` 无效，空字符串仅允许用于清空描述。
- Python 内部保留 UUID、datetime 和 Enum；跨 JSON 边界时显式使用 JSON 模式序列化。
- 后续 Service 应合并普通数据后重新调用 `model_validate()`；不使用不会重新校验更新值的 `model_copy(update=...)` 处理不可信变更。

## 正面影响

- 字段所有权可以从类型和测试中直接看出。
- 创建输入不能伪造 ID、状态和时间。
- 普通更新不能绕过未来的关闭业务规则。
- 持久化或读取数据缺少必需字段时会尽早失败。
- 后续 CLI、FastAPI 和工具调用可以复用同一组数据契约。

## 代价与风险

- 三个模型存在少量重复字段，需要同步维护共享约束。
- Pydantic 用 `T | None = None` 表达可省略字段时，也会接受 `null`，因此更新模型需要额外校验显式空值。
- `frozen=True` 只阻止常规属性赋值，并不是深层不可变或“所有复制操作自动校验”的保证。
- 新增可编辑字段时，必须明确它属于哪些输入模型，不能只修改读取模型。

## 验证方法

- 测试创建模型拒绝 `status` 等系统字段。
- 测试更新模型拒绝空更新、显式 `null` 和状态修改，但接受 `description=""`。
- 测试读取模型要求完整且有效的 UUID、状态和带时区时间。
- 测试 `model_dump(mode="json")` 生成可用于 JSON 的稳定值。
- 测试模型校验后不能直接修改字段。

## 重新评估条件

当业务需要更多更新动作、不同读取视图或内部领域实体时，可以引入共享组合类型或独立领域模型；在出现真实重复成本前不提前抽象。
